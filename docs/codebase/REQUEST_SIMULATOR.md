# REQUEST_SIMULATOR.md — `requestSimulator.ts` full trace-through

Content below reflects a complete fresh line-by-line re-read of the current file (1066 lines) during this pass. Line numbers cited are exact.

## 1. What a "request" is in this engine

There is no request object beyond `SimulationScenario` (`method`, `path`, `trafficLevel`, optional `startNodeId`). There is no payload, headers, or body — `scenario.path` is the only field inspected for content (used as a raw string for the WAF regex and CloudFront static-asset check). The "request" is really just a token that walks node-to-node through the graph; nothing about its content changes as it traverses except the accumulated `steps[]` trace and a running `currentTimestamp`.

## 2. Start-node determination (lines 19-41)

`serviceNodes` = all nodes that are `type === 'serviceNode'` or untyped-but-carrying a `serviceId` (i.e., explicitly excludes `boundaryNode`s). Start node priority, first match wins:
1. `scenario.startNodeId` if it names an existing service node.
2. First node with `serviceId` in `['user', 'client_ui', 'api_client']`.
3. First node with `serviceId` in `['internet_gateway', 'cloudfront', 'route53', 'alb', 'api_gateway']`.
4. `serviceNodes[0]` (whatever was added to the canvas first).

If there are literally zero service nodes, the function short-circuits with a canned `400`/"Canvas has no active AWS services" result before any step is created (lines 30-41).

## 3. Loop guards, evaluated first on every hop (lines 119-201)

In this exact order, before any service-specific behavior runs:
1. **Hop budget** (`MAX_HOPS = 40`, line 47): incremented and checked at the very top of the `while`. Comment explicitly notes this exists because a 2-node cycle (A→B→A) never grows the `visited` set, so a pure "have we seen this node" check cannot terminate it — only a hard hop ceiling can. Produces a `508`/"Routing Loop Detected" step.
2. **Node health** (line 146): if `currentNode.data.health === 'failed'`, immediately fails with `503` and the node's own `failureReason` (or a generic "offline" message).
3. **Subnet placement** (line 177): if `currentNode.data.subnet === 'unassigned'` (derived live by `containment.ts`, see `NETWORKING_CURRENT_STATE.md`), immediately fails with `400` — "not placed inside any Public or Private subnet boundary."

Only after all three pass does any BEHAVIOR block run.

## 4. Behavior blocks, in exact source order

## 5. Generic hop resolution (BEHAVIOR 7, lines 700-981) — reached whenever nothing above already `break`/`continue`d

1. **`nextNode`** = first downstream node not yet in `visited`, else `downstreamNodes[0]` (line 700) — this fallback-to-already-visited is exactly why the `MAX_HOPS` counter, not the `visited` set, is what actually terminates cycles (see §3).
2. **Dead end** (line 702): if `nextNode` is undefined (every outgoing edge points at a boundary container or a stale/missing id), `502` fail with an explicit "connections to boundary containers cannot carry traffic" explanation.
3. **7A — IGW attachment gate** (lines 733-798): only checked when the **current** node is a public origin (`user/client_ui/api_client`, or anything with derived `subnet === 'global'`) AND the **next** node is one of `{alb,nlb,elb,api_gateway,app_runner,ec2,ecs,fargate}` sitting in a `public` subnet. If no `internet_gateway` node exists anywhere on the canvas → `504` "No Internet Gateway Attached." If one exists but is `health: 'failed'` → `504` "Internet Gateway Outage." Fully-managed/edge services (CloudFront, Route 53, Lambda, S3, DynamoDB, etc.) are deliberately exempted by construction, since `isVpcHostedPublicTarget` only matches the fixed 7-id allow-list above.
4. **Managed event trigger** (lines 803-831): if the edge's own `protocol === 'Event'` and `nextNode.serviceId ∈ {lambda,sns,sqs,eventbridge,step_functions}`, emits an "S3 Event Notification" step (wording is hardcoded to the S3→Lambda scenario even though the condition is generic to any Event-protocol edge into any of those 5 targets) and either fails `500` (if `nextNode` unhealthy) or advances via `continue`. **No firewall check runs on this path either** — same gap as 6B.
5. **7B — direct public→private block** (lines 800-858): if current node is a public origin, next node's derived subnet is `private`/`isolated`, and next node is **not** one of the recognized ingress proxies (`alb,nlb,elb,api_gateway,cloudfront`) → `403` "VPC Ingress Violation," with a bottleneck entry appended.
6. **7C — private-subnet egress** (lines 860-956): triggers when the current node is in a private/isolated subnet (and is not itself an endpoint node) and the next node is external (`global` subnet or `api_client`/`user`) and not a DB (`rds`/`dynamodb` are explicitly excluded from being treated as "external" targets here, even though they can have `subnet === 'global'` in some layouts — this exclusion prevents a private compute node's normal DB call from being misclassified as "internet egress"). Sub-cases, in order: (a) a healthy VPC-endpoint-type node exists **and** the actual target is `s3`/`dynamodb` → routed through the endpoint, success; (b) no `nat_gateway` node exists at all → `504` "NAT Gateway Missing," bottleneck logged; (c) a `nat_gateway` exists but is `failed` → `504` "NAT Gateway Outage"; (d) healthy NAT gateway → SNAT success step.
7. **Firewall check** (line 958): `pushFirewallBlockIfAny(currentNode, nextNode, protocol)` — the shared closure (defined once near the top, lines 78-117) that runs `checkNetworkFirewalls` and pushes an explicit Allowed/Blocked step per **evaluated** layer (NACL first, then SG), stopping on the first block. A layer with no explicit rules configured produces no step and is invisible in the trace — this is why the vast majority of reference architectures (which don't configure `customNacl`/`naclDenyInbound`/`allowedProtocols` at all) show no firewall steps whatsoever.
8. **Default forward** (lines 962-980): generic "Forward `<protocol>` request" success/failure step (failure only if `nextNode.data.health === 'failed'` — note this is the **only** place in the entire generic-hop path that actually checks the next node's health before advancing; a healthy-looking forward can still terminate on the next loop iteration's top-of-loop health check at line 146), `currentTimestamp += 20`, `currentNode = nextNode`, loop continues.

## 6. Post-loop stateless-NACL return check (lines 983-1034) — FIXED

**Status: fixed.** Only runs `if (overallSuccess)` after the main loop exits. It previously did **not** use the actual traversed path — it re-scanned the **entire node list**:
```
const webComputeNode = serviceNodes.find(n => ['ec2','ecs','lambda','fargate'].includes(n.data.serviceId)) || startNode;
const dbNode = serviceNodes.find(n => ['rds','aurora','dynamodb'].includes(n.data.serviceId));
```
`.find()` returns the **first** node of that type in canvas array order — not necessarily the compute node and DB node actually visited on this particular successful run. In any diagram with more than one compute node or more than one database, this could evaluate the wrong pair's NACL configuration entirely, producing a stateless-return verdict for a node pair that had nothing to do with the request that just ran.

Fixed by introducing an ordered `path: Node<ServiceNodeData>[]` array (seeded with `startNode`, pushed to at every one of the 4 `currentNode = ...` reassignment sites in the traversal loop) and scoping both lookups to it:
```
const webComputeNode = path.find(n => ['ec2','ecs','lambda','fargate'].includes(n.data.serviceId)) || startNode;
const dbNode = path.find(n => ['rds','aurora','dynamodb'].includes(n.data.serviceId));
```
Verified decisive with a dedicated regression test (`test/engine.test.ts` test 43): a fixture with a decoy EC2/RDS pair (listed first in the node array, NACL configured to allow return traffic, never connected to the client) alongside a real pair (NACL configured to block return traffic, the only pair actually reachable from the client). Temporarily reverting the fix to the old whole-canvas scan was confirmed to flip this exact test from pass to fail (it picks the decoy pair and reports success instead of the correct 504), then the fix was restored and the full suite re-verified at 43/43.

## 7. Latency-accounting bug — FIXED

**Status: fixed.** When `checkCustomNaclReturn` blocks, the pushed step declares `latencyMs: 30000` and `timestampMs: currentTimestamp + 15` (line 995), but `currentTimestamp` itself was never incremented in this branch (contrast with the success branch two lines later, which does `currentTimestamp += 10`). The function's final return used the un-incremented `currentTimestamp` for `totalLatencyMs`, so a simulation result that failed via this stateless-return block reported a `totalLatencyMs` (confirmed reproduced: `104`ms) far lower than the `30000`ms the failing step itself claimed a client actually waited. Fixed by adding `currentTimestamp += 30000;` in the blocked branch, matching the pattern the success branch already used. Covered by `test/engine.test.ts` test 41 ("Stateless NACL Return Block Latency Is Reflected in totalLatencyMs").

## 8. Firewall-check coverage gaps (newly confirmed this pass)

`pushFirewallBlockIfAny` is called at exactly 3 sites: the ALB/API-Gateway target hop (line 497), the compute→DB hop (line 553), and the generic default-forward hop (line 958). It is **not** called on: the explicit VPC-endpoint hop (6B, line 672-695), the managed-event-trigger hop (line 803-831), or the private-subnet-egress-via-NAT hop (7C, line 860-956, though 7C's own sub-branch that routes through an endpoint at line 869-886 is a different code path than the main firewall check and also skips it). This means a Security Group or NACL configured on a target reachable only through one of these three paths can never actually block traffic in the simulation, even if the same target is otherwise correctly protected when reached via ALB or a generic edge. Not previously documented; a genuine coverage gap in the firewall model, not by design (no comment in the code explains or justifies the omission on these 3 paths, unlike the deliberate documented exclusions elsewhere in the file).

## 9. Everything is a fixed literal-string conditional chain, not a modular engine

Every BEHAVIOR block above is a top-level `if` inside one 850-line function, keyed directly on `currentNode.data.serviceId` or `nextNode.data.serviceId` string literals. There is no dispatch table, no per-service "behavior" interface, no plugin/extension point — adding a new differentiated behavior for service #29 means adding another `if (currentNode.data.serviceId === '...')` block to this same function and manually deciding where in the existing sequence it needs to slot in relative to the other 8 behaviors (an easy place to introduce ordering bugs, as behaviors are order-sensitive: e.g. BEHAVIOR 1's WAF check must run before BEHAVIOR 5's ALB routing, or a malicious request would reach a backend target before being inspected). This is the "giant conditional chain keyed on service type" anti-pattern flagged generally in this project's earlier audit pass, now traced through its exact concrete form.
